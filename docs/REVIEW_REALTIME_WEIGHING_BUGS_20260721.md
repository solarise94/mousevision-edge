# 实时称重 Bug 核验报告与修改方案

- 日期：2026-07-21
- 范围：手机端实时称重、WebSocket 帧流、实时称重状态机、TTS 播报
- 用户现象：称重结果出现慢；“重测”像是点不了；没有语音播报；截图中秤面约为 `15.62 g`，页面候选为 `16.14 g`
- 约束：本报告只核验问题并给出修改方案，不修改业务代码

## 1. 结论摘要

本次不是一个单点故障，而是四个问题叠加：

| 编号 | 问题 | 核验结论 | 优先级 |
|---|---|---|---|
| RT-01 | 稳定判定会复用旧样本，可能过早锁定旧体重 | **已复演确认**；与截图数值高度吻合 | P0 |
| RT-02 | “重测”前后端状态不同步，且命令可能排在旧图像帧后面 | **代码确认**；足以造成“点了没反应” | P0 |
| RT-03 | iPhone Safari TTS 首次调用缺少用户手势预激活，失败被静默吞掉 | **代码缺陷确认**；具体失败分支需真机日志最终定性 | P1 |
| RT-04 | 当前至少需要多层连续帧才能播报，鼠检测还是硬门槛 | **代码确认**；会造成固有等待，检测抖动时等待会明显放大 | P1 |

没有发现按钮被 CSS 遮挡或 `pointer-events` 禁用的证据。按钮 DOM 事件确实已绑定，因此“点不了”更像是协议排队和错误的乐观 UI 状态，而不是触摸区域本身失效。

## 2. 核验依据

### 2.1 RT-01：旧体重可被重复输出并触发错误播报

当前流程包含两层连续判定：

1. `TemporalWeightFusion` 用 8 帧滑窗、至少 3 票得到一个 stable 输出；
2. 实时状态机又要求累计 4 个 stable 输出后才播报。

第二层累计的不是四组独立原始读数，而是四次高度重叠的滑窗结果。同一批旧读数因此可以被重复计数。

用截图中的数值按当前配置复演原始序列：

```text
原始 OCR：16.14, 16.14, 16.14, 15.62, 15.62, 15.62
融合输出：  空,    空,  16.14, 16.14, 16.14, 16.14
```

第四个 `16.14` stable 输出会满足 `stable_min_frames=4`，此时实时状态机可播报并锁定 `16.14`，尽管最新三帧已经全部是 `15.62`。这与截图“秤面 15.62、页面 16.14”高度一致。

相关实现：

- `mousevision/fusion/temporal.py:152-232`：滑窗聚类、旧平台 stick 与重复 stable 输出；
- `mousevision/realtime.py:521-543`：再次累计 stable 输出并取均值播报。

风险不仅是慢，还包括错误确认：页面在 `ANNOUNCED` 状态不再读取新重量，只持续展示已经锁定的 attempt，因此秤面随后变化时页面也不会撤销候选。

### 2.2 RT-02：“重测”并非没有事件，而是状态与队列设计使其看起来无效

前端点击“重测”后执行以下动作：

1. 停止新增帧 400 ms；
2. 立即向同一 WebSocket 发送 `retry`；
3. 不等待 ACK，直接把本地 UI 改成 `armed` 并隐藏按钮。

这里有三处确定问题：

- WebSocket 保证 FIFO。服务端循环逐条处理图片帧和文本命令；已经进入连接/服务端队列的旧帧无法被 `drainSendQueue()` 清除，因此 `retry` 会排在旧帧之后；
- `drainSendQueue()` 实际没有等待 `ws.bufferedAmount` 清空，只停止后续定时器 400 ms，函数名和行为不一致；
- 即使 `rtSend()` 返回 `false`，前端仍然清空候选并切到 `armed`，没有错误提示。

更关键的是后端收到 retry 后并不会进入 `armed`，而是进入 `retry_requested`，并要求先读到一帧空秤才允许重新称重。若小鼠仍留在秤上，会一直等待，最长可到 30 秒。前端既没有对应中文状态，也没有提示“请先取走小鼠”，所以用户会认为按钮没有生效。

相关实现：

- `ui/static/mobile.js:1454-1479`：乐观切状态与名义上的 drain；
- `ui/static/mobile.js:1481-1529`：只依据浏览器网络缓冲限流，没有依据服务端处理完成 ACK 限流；
- `ui/realtime_api.py:815-866`：服务端在同一接收循环中按顺序处理帧和命令；
- `mousevision/realtime.py:226-239,605-631`：retry 进入 `RETRY_REQUESTED`，等待空秤；
- `ui/static/mobile.js:1324-1388`：前端没有 `retry_requested` 的状态文案和 UI 分支。

### 2.3 RT-03：TTS 调用链存在 iOS Safari 兼容缺口

当前仅在收到新 `attempt` 的 WebSocket 消息时调用一次 `speechSynthesis.speak()`。该调用发生在异步网络回调里，不属于点击等用户手势；页面启动时也没有通过用户手势预激活语音能力。

代码还存在以下可观测性缺口：

- utterance 只保存在函数局部变量中；
- 没有等待/选择中文 voice；
- 没有监听 `onstart`、`onend`、`onerror`；
- 所有异常均被空 `catch` 吞掉，页面也不提示；
- 重连时 `hello` 只恢复状态，不会补播当前 announced attempt。

因此从现有日志无法区分：浏览器策略阻止、没有可用中文 voice、设备静音、utterance 被中断，还是调用根本没有开始。用户的 iPhone Safari 现象与这一缺口相符，但最终归因仍应通过真机 `onerror` 和播放事件确认。

相关实现：`ui/static/mobile.js:1291-1300,1395-1431`。

### 2.4 RT-04：当前固有等待较长，并且鼠检测会重置稳定进度

理想 4 fps 下，从小鼠放上秤开始至少要经过：

- `ARMED`：2 个连续非零帧；
- `WEIGHING`：融合至少 3 个一致原始读数；
- 实时层：累计 4 个 stable 输出。

由于 stable 第一次可在第 3 个 WEIGHING 帧出现，理论最短约为 2 个 ARMED 帧 + 6 个 WEIGHING 帧，即约 **2.0 秒**。若放鼠时仍在 5 帧校准期，还要再增加最多约 1.25 秒。任何 OCR 无结果、鼠检测抖动或网络排队都会继续延长。

此外，离线配置写明鼠检测是 advisory，但实时路径在 `mouse_present=false` 时会直接清空 `_stable_run`。检测只要间歇性漏掉黑鼠、尾巴姿态或秤盘边缘，就会反复从零计数。

相关实现：

- `mousevision/realtime.py:76-101`：默认门槛；
- `mousevision/realtime.py:295-322`：鼠检测及多数平滑；
- `mousevision/realtime.py:493-527`：鼠检测为播报硬门槛；
- `configs/scale_refvideo.yaml:169-171`：主流程配置说明鼠检测应为 advisory，与实时实现不一致。

本机在一张 720×1280 回归帧上测得：`lcd_box` 约 1.13 ms、`read_weight` 约 8.43 ms、当前 WEIGHING 路径合计约 9.56 ms。该数据只说明本机纯 OCR 不是主要瓶颈，不能代替生产服务器和 iPhone 网络测量。当前 WEIGHING 每帧还重复定位 LCD 两次，可作为优化项，但不是此次“半天才出结果”的首要解释。

## 3. 现有测试为何没有拦住

执行：

```text
python3 -m pytest -q tests/test_realtime.py tests/test_realtime_contract.py
19 passed in 1.85s
```

测试覆盖了恒定体重下的状态转换、engine retry/accept，以及“一帧处理完后再发送命令”的协议 happy path，但没有覆盖：

- 稳定平台从 `16.14` 快速切换到 `15.62`；
- 滑窗输出被第二层稳定计数重复使用；
- 多张图片已经排队时插入 retry/accept 命令；
- `rtSend=false`、ACK 超时、断线重连；
- `retry_requested` 在手机端的真实 UI；
- iOS Safari 的 TTS 用户手势、voice 加载和错误事件。

所以当前测试通过只能证明基本状态机没有崩溃，不能证明这三个用户路径正常。

## 4. 修改方案

### P0-1：合并稳定判定，禁止重复计算重叠窗口

推荐只保留一层以“独立原始 OCR 帧”为输入的稳定窗：

1. 进入 WEIGHING 时清空窗口并记录 `weighing_epoch`；
2. 只接收该 epoch 之后、`frame_seq` 唯一且时间戳递增的原始读数；
3. 最近 3–4 个有效原始读数在 0.5–0.8 秒内，`P90-P10 <= 0.10~0.15 g` 才产生候选；
4. 候选必须包含最新一帧；最新原始读数与候选差值超过阈值时立即撤销候选；
5. 最终重量取这组原始读数的中位数，不取重复 fusion 输出的均值。

若必须保留 `TemporalWeightFusion`，则它应返回本次 stable 所依赖的原始 `frame_seq` 集合或窗口版本；实时层只能在窗口版本真正前进、且新增独立原始样本时计数，不能把同一滑窗的重复输出当作新证据。

必须新增回归：`16.14 × 3 -> 15.62 × 3` 不得播报 `16.14`；最终只有最新平台自身满足稳定窗后才能播报 `15.62`。

### P0-2：用服务端处理 ACK 做“最多一帧在途”，让控制命令可抢占

推荐协议：

- 客户端发送一帧后等待对应 `frame_seq` 的 state/ack，再发送下一帧；
- 超时后丢弃该帧，发送最新画面，不补发历史画面；
- 客户端只保留一个 latest-frame slot，不维护图片 FIFO；
- 点击 retry/accept 时立即停止出帧，等待至多一个在途帧完成，然后发送命令；
- 收到命令 ACK 后再恢复出帧；
- 服务端记录 `captured_at / received_at / processing_started_at / completed_at`，可直接看到帧龄与处理耗时。

这比继续调低 `WS_BACKPRESSURE_BYTES` 更可靠，因为浏览器的 `bufferedAmount` 只反映网络发送缓冲，不反映服务端 OCR 队列深度。

### P0-3：明确“重测”的产品语义并统一前后端

推荐语义：**同一只鼠可以留在秤上重测**。

点击后：

1. 服务端拒绝当前 attempt；
2. 增加 `weighing_epoch`，丢弃旧 epoch 的在途结果；
3. 清空融合/稳定窗口；
4. 直接进入 WEIGHING，从点击之后的新帧重新采样；
5. ACK 返回明确的 `accepted: true/false`、新 state 和 epoch；
6. 前端收到 ACK 后才切状态，按钮在等待期间显示“正在重测…”。

如果业务坚持必须把鼠拿下再放回，则按钮应改成“放弃本次”，并明确显示“请先取走小鼠，再放回重测”；不能把本地 UI 乐观改成“待称重”。两种语义只能选一种，不能维持当前前端 `armed`、后端 `retry_requested` 的分裂状态。

### P1-1：建立可控、可观测的 TTS 管理器

推荐顺序：

1. 在进入实时称重的用户点击手势中做一次静音/极短语音预激活；若当前页面没有显式按钮，增加“开启语音并开始称重”；
2. 保留当前 utterance 的强引用，上一条结束后再释放；
3. 等待 `voiceschanged`，优先选择 `zh-CN` 本地 voice；
4. 监听 `onstart/onend/onerror`，失败时 UI 显示“语音未播放，点此重播”；
5. 以 `attempt_id` 去重，避免重复 state 消息重复播报；
6. 重连恢复 announced attempt 时允许补播一次；
7. Web Speech 仍不稳定时，增加短提示音 + 服务端生成的中文音频作为降级路径。

不要再用空 `catch`。至少把浏览器、voice、attempt_id 和 error code 记到客户端诊断日志。

### P1-2：降低等待但不牺牲准确性

- 用时间窗代替固定帧数，避免实际 fps 下降时等待成倍变长；
- 鼠检测改为 advisory：重量稳定且读数可信时允许播报；鼠检测缺失只降低置信度或显示提示，不应清空全部稳定证据；
- 同一帧只定位一次 LCD，把 box 传给读数解析和鼠检测，消除重复图像处理；
- 把 realtime 专用阈值放入 YAML 并完整加载。目前 `_create_engine()` 只读取少量 RealtimeConfig 字段，调整主配置中的多数参数不会影响实时路径。

## 5. 建议验收标准

### 功能

- `16.14 × 3 -> 15.62 × 3` 不得锁定或播报旧的 `16.14`；
- retry 在小鼠不离秤时也能按选定产品语义重新采样，状态和文案一致；
- WebSocket 断开或命令发送失败时，按钮不得假装成功；
- iPhone Safari 首次 attempt 有明确的播报成功或可见失败提示。

### 性能

- 从首个有效非零读数到候选：P50 ≤ 1.2 秒，P95 ≤ 2.0 秒；
- 服务端开始处理时的帧龄：P95 ≤ 500 ms；
- retry 点击到 ACK：P95 ≤ 500 ms；
- 任意时刻服务端每会话待处理图片不超过 1 张。

### 准确性

- 播报候选与播报时最新有效原始读数差值 ≤ 0.15 g；
- 候选证据全部来自同一 `weighing_epoch`；
- 每个稳定证据对应唯一原始 `frame_seq`。

### 真机矩阵

- iPhone Safari：至少覆盖当前现场机型与一个较旧 iOS 版本；
- Android Chrome：覆盖正常网络与 300–500 ms 人工延迟；
- 断线重连、弱网、连续快速点 retry、秤上不取鼠、取鼠后重放都要录屏并保存协议时间线。

## 6. 推荐实施顺序

1. 先修 RT-01 稳定证据复用，避免错误体重被确认；
2. 再修 RT-02 单帧在途与 retry 状态契约，解决“慢”和“按钮无响应”；
3. 加 TTS 预激活与错误可见化；
4. 最后基于埋点调整稳定时间窗，不能只靠降低帧数阈值追求更快；
5. 小流量部署，至少收集一轮真实称重的帧龄、状态耗时、候选撤销率和 TTS 事件后再全量。

## 7. 本次未做事项

- 未修改任何业务代码或配置；
- 未在现场 iPhone 上接入 Safari Web Inspector，因此 TTS 的具体错误码仍待真机补证；
- 未把截图 OCR 当作地面真值。截图中的 LCD 数值由肉眼读取，RT-01 的结论来自代码序列复演与该数值的一致性。
